## 现象

分割模型接进实时推理之后，日志里开始出现这样的框：

```text
box=[568, 0, 639, 0]
```

`y1 == y2 == 0`，高度为零。所有框都贴在图像最上边，宽度还各不相同。模型本身是有输出的——置信度不低，类别也对——但框没有意义。

## 逆变换做了什么

预处理时，原图被等比缩放后放进一个 640×640 的方形输入，空出来的地方补灰。这块补边就是 letterbox padding。

拿一个假设的尺寸算一下：原图为 720×1280（高×宽），等比缩放系数是 `min(640/720, 640/1280) = 0.5`。缩放后得到 360×640（高×宽），于是上下各补 `pad_y = (640 - 360) / 2 = 140`，左右不补，即 `pad_x = 0`。

后处理拿到的是**640×640 坐标系**下的框，要回到原图，就得把缩放和平移反向做一遍：

```text
x_orig = (x_net - pad_x) / scale
y_orig = (y_net - pad_y) / scale
```

这个算例没有遇到缩放取整。实际项目要沿用预处理时记录的缩放和补边参数；如果取整后两个方向的实际比例不同，就按实现的坐标约定分别处理，别自己猜。

如果一个高置信候选框完全落在**上方的 padding 区域**——本来是灰色补边，模型偶尔也可能在那里给出响应——它的两个纵坐标都不大于 `pad_y`。减去 `pad_y` 后再除以 `scale`，两个值都不大于 0；经过 `clamp(0, H)`，两端就都变成 0。

例如网络输入上的框是 `[200, 100, 400, 120]`，逆变换后是 `[400, -80, 800, -40]`，裁剪到原图边界后就成了 `[400, 0, 800, 0]`。这只是解释坍缩方式的算例，不是实测的原始框。如果只有框的一部分落在补边里，裁剪后也可能仍有非零高度。

## 修法

短期的修法是在后处理里加一道无效框过滤，同时把诊断信息打出来。下面是示意：`conf_passed_boxes` 是本帧通过置信度筛选的候选框，`first_invalid_logged` 在每帧开始时置为 `false`、放在循环外，因此每帧最多打印第一个无效框。

```cpp
const auto conf_pass = conf_passed_boxes.size();
int valid = 0;
int invalid_box_count = 0;
bool first_invalid_logged = false;

for (const auto& raw_box : conf_passed_boxes) {
    auto [x1, y1, x2, y2] = inverse_and_clamp(raw_box);  // 示意函数
    if (x2 <= x1 || y2 <= y1) {
        if (!first_invalid_logged) {
            LOG(INFO) << "[Seg] Drop invalid box: " << raw_box;
            first_invalid_logged = true;
        }
        ++invalid_box_count;
        continue;
    }
    ++valid;
    // 保留有效框，继续后处理
}
// 每帧汇总一次
LOG(INFO) << "[Seg] Filtered invalid boxes: conf_pass=" << conf_pass
          << " valid=" << valid << " invalid_box=" << invalid_box_count;
```

这条统计比想象中有用。它把两种情况分开了：

- `valid = 0` 且 `invalid_box` 很多：这一帧没有候选框通过宽高检查，值得回查补边、逆变换和输出布局；单凭计数还不能确定是哪一步出了问题；
- `valid > 0`：有候选框通过了这道宽高检查，但它们是不是正确目标，仍要对照原图和 mask 判断。

过滤只能拦住这类无效框，不能替代修正真正有问题的坐标变换。

## 复盘

这次的问题不复杂，但很典型：**letterbox 把图像挪进了另一个坐标系，逆变换没被单独验证过**。

以后再遇到「模型有输出但结果不对」，我会先回答三个问题：

1. 这个坐标现在属于哪个坐标系？（网络输入 / 原图 / 相机系）
2. 逆变换的每一步，有没有可能在某个端点产生负数或者越界？
3. 越界之后，代码是**报错**、**丢弃**，还是**悄悄 clamp**？

第三个问题最关键。`clamp` 是一种温柔的失败：它让程序继续跑，只是结果错了。如果当时没有打印那条「被丢弃的框」，我可能会在错误的坐标上继续调模型，浪费一整天。
