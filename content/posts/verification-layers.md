## 「已完成」是最危险的三个字

过去半年我大部分代码是和 Codex 一起写的。它很快，但有一个习惯特别需要警惕：**它会把「我写了代码」说成「问题解决了」**。

「已修复」「已通过」「应该可以了」——这些话在看到真实输出之前，都只是**关于代码的陈述**，不是**关于系统的陈述**。中间隔着好几道门，每道门都可能关着。

所以现在我对任何一次改动，都按下面的顺序问自己：**我到底验证到了第几层？**

## 六层验证

| 层 | 检查什么 | 通过不意味着 |
| --- | --- | --- |
| 1. 文本 / 差异 | 补丁是否完整、有没有误删、空白是否干净 | 能编译 |
| 2. 语法 / 局部编译 | 这个文件、这个 target 能不能过编译器 | 能链接 |
| 3. 完整构建 | 整个工程链接是否通过 | 运行期正确 |
| 4. 单元 / 数值 | 这段逻辑在已知输入上是否给出预期数值 | ABI / 运行时正确 |
| 5. ABI / Runtime | 插件、算子、序列化协议是否真的被加载 | 真机可用 |
| 6. 真实设备 | 摄像头、机械臂、CUDA 驱动是否真的按预期工作 | 现场一定稳定 |

`git diff --check` 只检查空白错误。它通过了，第 2 层还没开始。

CMake 能 configure，不等于能 build。`target_link_options()` 写在 `add_executable()` 之前，配置阶段就会报错——这类问题我在一次推理程序里真的遇到过，改法只是把这两行调换顺序，但它拦住的是整条流水线。

编译通过，不等于链接通过。两个静态库里有同名全局类，会到链接期才炸，而且报错信息指向的是一个和业务毫无关系的位置。

链接通过，不等于 ABI 匹配。CUDA 核函数跑通了，但 schema 没对上，完整 ABI 仍然是断的——这种时候「核心通过」和「功能可用」是两件事。

**每一层只证明它自己那一层。** 第 4 层通过，不能用来安慰第 6 层的失败。

## 两个配套习惯

**第一，把猜测和确认分开写。** 日志相关性只能支持一个嫌疑，不能证明根因。确认根因需要最小 A/B、行为复测或者明确的接口证据。所以我在记录里会写清楚：「这条是已确认的」「这条只是嫌疑」。

**第二，失败不要伪造成功输出。** 没有有效位姿时，不要输出零位姿或者上一帧的旧位姿——那会让下游以为一切正常。宁可让流程显式失败，也不要把错误藏进一个看起来合理的结果里。

## 说清楚「验证到哪」

现在我在写交接、写文档、甚至写这篇文章时，都会尽量带上范围：

> 本机 x64 编译通过；aarch64 未构建；真机未复测。

这句话看着啰嗦，但它比一百个「已修复」有用。因为它把**不确定的部分**也交出去了，读的人才知道下一步该验证什么。
