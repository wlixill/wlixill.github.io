## 一次差点发生的误删

有一次 AI 在帮我看一个分支问题，顺手建议：

```bash
git reset --hard origin/main && git clean -fd
```

理由是「本地改动看起来是构建产物」。但那个工作区里还有我写到一半的笔记和两个没提交的补丁。如果照做，它们会一起消失。

从那之后我把几条 Git 纪律写进了给 AI 的常驻提示里。

## 四条底线

**第一，只 stage 与本次任务相关的文件。** 不要用 `git add -A`、`git add .`。工作区里经常混着构建产物、日志、临时笔记，一把梭会把不该提交的东西带进去。

**第二，不要用 `reset --hard`、`checkout --`、`stash` 去「清理」别人（包括我）的工作。** 需要回退时，先看 `git status` 和 `git diff`，只对确认无用的文件动手。

**第三，父仓库和子仓库分开处理。** 子模块显示为 `M`，可能只是它的 HEAD 变了，也可能真的有未提交改动。要先 `git -C submodule status`，再决定要不要动。把父仓库的提交和子模块的提交混在一次操作里，最容易出现「某一边没跟上」的错位。

**第四，一次授权只对应一次操作。** 「上次你同意我清理历史，所以这次也可以」——这种推理是错的。删除历史、强推、改远端这类操作，每次都要重新确认。

## 一个具体的例子

嵌套的仓库被当成普通目录加进父仓库，是很容易发生的事：

```bash
git add vendor/sub-project
# 结果：子模块里的 .git 被忽略，文件被当成普通文件提交
```

等发现的时候，历史里已经多了一堆本该由子模块管理的文件。要修就得重写历史，而重写历史又会牵扯远端和协作者。

所以现在的顺序是：**先看仓库边界，再谈提交**。

## 为什么在 AI 时代更要写下来

人做这些操作前会犹豫一下，AI 不会。它会把「清理工作区」当成一个合理的步骤，然后执行得很彻底。

底线写在提示里，比每次事后解释要便宜得多。
